## 1. OpenFisca and PolicyEngine: metadata fields on parameters and variables

### Takeaway
A parameter is a YAML file with three kinds of top-level key (`description`, `metadata`, and one of `values` / `brackets` / child nodes); everything else (unit, period, label, reference, breakdown, uprating, scale type) lives under `metadata`, which is a free dictionary that the loader does not validate against a closed vocabulary. A variable is a Python class whose class attributes (`value_type`, `entity`, `definition_period`, `label`, `unit`, `reference`, `defined_for`, `adds`, `subtracts`) are the metadata, and whose `formula` is the rule.

**Parameter file keys**
- [read directly] OpenFisca documents the parameter attributes as: `description` (optional); `metadata` (optional) containing `reference` (optional, "Legislative reference") and `unit` (optional); and `values` ("Value of the parameter for several dates"). — [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md)
- [read directly] OpenFisca's documented `unit` values are exactly three: `year` ("The values are years"), `currency` ("The values are in the unit of currency of the country"), `/1` ("The values are percentages, with `1.0`=100%"). The scale example in the same page uses `threshold_unit: currency-EUR` and `rate_unit: /1`. — [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md)
- [read directly] OpenFisca naming rule: names "should begin with a lowercase letter and should contain only lowercase letters and the underscore". Reserved words: `description`, `reference`, `values`, `brackets`. A parameter's dotted name is its file path (`tax_on_salary.public_sector.rate` is `parameters/tax_on_salary/public_sector/rate.yml`). — [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md)
- [read directly] openfisca-core: `ALLOWED_PARAM_TYPES = (float, int, bool, type(None), list, str)`; `COMMON_KEYS = {"description", "metadata", "unit", "reference", "documentation"}`. — [openfisca-core parameters/config.py](https://github.com/openfisca/openfisca-core/blob/db0484b54871b0a73e673478b3153841dba908e9/openfisca_core/parameters/config.py)
- [read directly] policyengine-core: `ALLOWED_PARAM_TYPES = (float, int, bool, type(None), typing.List)` (no `str`); `COMMON_KEYS = {"description", "metadata", "documentation"}`; `LEGACY_COMPAT_KEYS = {"reference", "unit"}` are tolerated beside `values:` "even though the current convention nests them under `metadata:`". **Scales / brackets**
- [read directly] A scale file has `brackets:` (a list) instead of `values:`. Each bracket may hold the components `amount`, `threshold`, `rate`, `average_rate`, `base`, each a dated series. Matching unit keys are the component name plus `_unit` (`amount_unit`, `threshold_unit`, `rate_unit`, `average_rate_unit`, `base_unit`) and are copied from scale metadata to each bracket component's `unit`. — [policyengine-core parameter_scale_bracket.py](https://github.com/PolicyEngine/policyengine-core/blob/7c84d941be767309e1c24381a67635b8b8bf458d/policyengine_core/parameters/parameter_scale_bracket.py), [parameter_scale.py](https://github.com/PolicyEngine/policyengine-core/blob/7c84d941be767309e1c24381a67635b8b8bf458d/policyengine_core/parameters/parameter_scale.py)
- [read directly] Scale kind is resolved thus: `metadata.type == "single_amount"` gives a single-amount scale (lookup: returns the one cell for the bracket the input falls in); otherwise any `amount` component gives a marginal-amount scale (sum of cells up to the bracket); otherwise any `average_rate` gives a linear average-rate scale; otherwise a marginal-rate scale. OpenFisca's doc names the types `marginal_rate`, `marginal_amount`, `single_amount`. — [policyengine-core parameter_scale.py](https://github.com/PolicyEngine/policyengine-core/blob/7c84d941be767309e1c24381a67635b8b8bf458d/policyengine_core/parameters/parameter_scale.py), [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md)
- [read directly] Bracket edges: "By default, the interval includes the left but not right edge. To reverse this, use `scale.calc(salary, right=True)`." Edge inclusion is therefore chosen in the formula, not recorded in the parameter. The Colorado CTC formula calls `.calc(agi, right=True)`. — [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md), [co_ctc.py](https://github.com/PolicyEngine/policyengine-us/blob/ca7a4702718ca5d0a3f544cd73535e882d501930/policyengine_us/variables/gov/states/co/tax/income/credits/ctc/co_ctc.py)
- [read directly] Open-ended lowest bracket is written `-.inf`; an unlimited cap is written `.inf` (CollegeInvest `max_amount`, 2021). — [co ctc/amount/single.yaml](https://github.com/PolicyEngine/policyengine-us/blob/ca7a4702718ca5d0a3f544cd73535e882d501930/policyengine_us/parameters/gov/states/co/tax/income/credits/ctc/amount/single.yaml), [co collegeinvest max_amount.yaml](https://github.com/PolicyEngine/policyengine-us/blob/ca7a4702718ca5d0a3f544cd73535e882d501930/policyengine_us/parameters/gov/states/co/tax/income/subtractions/collegeinvest_contribution/max_amount.yaml)

### Inferences
- `metadata` is an open dictionary: only the top-level keys are checked. The unit vocabulary (`currency-USD`, `/1`, `year`, `bool`, `list`, `person`, `child`) is convention, not an enforced enumeration. A Colorado dictionary that wants a closed unit list has to enforce it itself.
- Several Colorado CTC scale files declare `type: single_amount` with `amount` brackets but give the unit as `rate_unit` (both `rate_unit: currency-USD` and `rate_unit: /1`). Because unit propagation maps `rate_unit` to a `rate` component, that unit does not reach the `amount` values. This shows the cost of unvalidated metadata.
- Three things a tax dictionary needs are absent from the parameter model: bracket edge inclusion (lives in the formula's `right=True`), inclusive/exclusive sense of an age or income threshold (carried only in the `description` prose, e.g. "maximum age (exclusive)", or in a separate boolean such as `eligible_at_max_age`), and what the amount is measured per (per return, per child, per person; only `unit: person` / `threshold_unit: child` hint at it).
- `period: year` on every Colorado parameter means the model keys values to tax years by a `YYYY-01-01` start date; there is no separate field for "tax years beginning on or after" versus a calendar effective date.

### Gaps
- I did not find a published, authoritative list of allowed `unit` values for policyengine-us (only the constants file and usage). The names of two policyengine-core variable attributes whose docstrings I read ("whether the variable is a stock or a flow"; "hidden from the input screen") were not captured, so they are not named here.
- I did not confirm where the `USD` constant used in variable classes (`unit = USD`) is defined, only that policyengine-core defines `USD = "currency-USD"`.
- openfisca.org itself was not fetched; OpenFisca statements come from the openfisca-doc and openfisca-core repositories.

## 2. policyengine-us Colorado model: directory tree, parameter kinds, examples, citation practice

### Takeaway
Colorado individual income tax in policyengine-us is 78 parameter files and 58 variable files arranged by return structure (additions, subtractions, credits, AMT, rate), and the parameters fall into about ten recurring kinds. Citation is by lists of `title`/`href` pairs that mix statute pinpoints, session-law sections, DOR form-book lines with PDF page anchors and agency web pages, with the which-source-governs reasoning kept in YAML comments.

**Citation conventions** [read directly; same tree]
- Every parameter has `metadata.reference` as a list of mappings with `title` and `href`. Titles take these forms: statute with pinpoint ("C.R.S. 39-22-104(4)(g)(III)(B)"; "C.R.S. 39-22-104 . - `href` for a PDF ends in `#page=N`; one title embeds "#page 7,10" when two pages matter. Statute links point to several different hosts (law.justia.com with a year in the path, advance.lexis.com session URLs, leg.colorado.gov and olls.info compilation PDFs, colorado.public.law).
- One reference list covers all years: a new form book is appended each year. References are not tied to individual dated values, although the loader supports per-value `metadata.reference`.
- At least one file gives the quoted statutory words inside the reference title (`cdcc/uses_federal_credit_before_liability_limitation.yaml`: "... 'seventy percent of the federal credit allowed pursuant to section 21 ... calculated without regard to the limitation imposed by section 26'").
- Authority and interpretation notes are YAML comments, not fields: "THE FOLLOWING THREE REFERENCES JOINTLY DETERMINE THE TAX RATE ON THE FORM"; "DOR set the single amount at $750"; "(3)(p.7) names only 'single return' and 'joint return'".
- `description` follows a fixed sentence pattern beginning with the jurisdiction and an active verb: "Colorado taxes personal income at this flat rate."; "Colorado matches this fraction of the federal Earned Income Tax Credit."; "Colorado limits ... to filers above this age threshold."; "Colorado counts these sources as subtractions." `label` is a short noun phrase beginning "Colorado ...".

### Inferences
- The provision types implied by this tree are: rate imposition; conformity starting point (federal taxable income); addition (add-back); subtraction with cap and eligibility; credit as a match of a federal credit; credit as a fixed amount by income band; phase-out; eligibility test; aggregation list; refundable/non-refundable ordering; one-time refund; contingent or triggered provision; AMT.
- PolicyEngine models contingency (TABOR-triggered rate cuts, revenue-triggered credit amounts) by storing the realised or expected outcome as a dated value and explaining the trigger in a comment. The trigger condition itself is not data.
- Parameter references cite the form book for every year but the statute once; the link from a dated value to the specific instrument that set it is recoverable only from comments.

## 3. Catala: tying code to legal text, default logic and exceptions, unit of legal text

### Takeaway
Catala source files are the legal text with code blocks interleaved: Markdown-style headings carry the article title (and optionally an article identifier and an archive flag), and the runtime attaches the enclosing headings to every code position. Rules are written as a base `definition` or `rule` plus `exception`s tied by `label`, a static encoding of prioritised default logic in which exactly one definition may apply or execution aborts.

### Cited Findings
- [read directly] Catala "enables a literate programming style, where each paragraph of law is immediately followed by its Catala transcription"; the worked example proceeds paragraph by paragraph of IRC section 121 ((a), then (b)(1), then (b)(2)(A)), inserting "a textual copy of the legal prose for (b)" and then transcribing it. — [Merigoux, Chataing, Protzenko, ICFP 2021, section 3.3](https://arxiv.org/abs/2103.03198)
- [read directly] Stated design aim: "we wish to remain close to the legal text, so that the formal specification remains in close correspondence with the reference legal text, and can be understood by lawyers." — [ICFP 2021 paper, section 3](https://arxiv.org/abs/2103.03198)
- [read directly] "Metadata" in Catala means the declarations of structures, entities and variables, written before any rule: "before even talking about how things are computed, we state what we are talking about"; the first task is "to enumerate all structures, entities and variables relevant to the problem at stake" because legal prose "uses a number of concepts without explicitly defining them in the text" (time periods, return types, the taxpayers). — [ICFP 2021 paper, section 3.1](https://arxiv.org/abs/2103.03198)
- [read directly] `scope` is the module unit: "scopes allow the programmer to follow the law's structure, revealing the implicit modularity in legal texts"; a scope can be split across the document so each fragment sits under the paragraph it implements. — [ICFP 2021 paper, sections 3.1 and 3.3](https://arxiv.org/abs/2103.03198)
- [read directly] `rule X under condition C consequence fulfilled` is for booleans ("conditions"); `definition X equals E` is for data. The reason given: "booleans (conditions) are false by default in the law; however, other types of data have no default value." Rules desugar to definitions with default `false`. — [ICFP 2021 paper, section 3.2](https://arxiv.org/abs/2103.03198)
- [read directly] Exceptions: `exception definition gain_cap under condition paragraph_A_applies consequence equals $500,000` overrides the base `definition gain_cap equals $250,000`. "if, at run-time, more than a single applicable definition for any context variable applies, program execution aborts with a fatal error"; the `exception` keyword gives the later definition higher priority. "only one single definition should be applicable at a time, and any violation of that rule indicates either programmer error, or a fatal flaw in the law." — [ICFP 2021 paper, section 3.4](https://arxiv.org/abs/2103.03198)
- [read directly] Labels: "all exceptions and definitions are labeled, and each exception refers to the definition or exception it overrides"; exceptions to exceptions are supported and "are actually found in the law"; definitions and exceptions form "a forest, with exactly one root definitions node for each variable X, holding an n-ary tree of exception nodes". Priorities are "encode[d] statically in the surface syntax", not resolved at run time. Semantics: if two or more exceptions are valid a conflict error is raised; if exactly one is valid it is the result; if none, the base applies when its condition is true, else the value is empty. — [ICFP 2021 paper, sections 3.2 and 4.1](https://arxiv.org/abs/2103.03198)
- [read directly] The foundation is prioritised default logic, citing Lawsky's argument that it is "the best suited to expressing the law". — [ICFP 2021 paper, section 2.7](https://arxiv.org/abs/2103.03198)
- [read directly] Intermediate applicability variables are named after the provision: `paragraph_A_applies`, `paragraph_3_applies`; an auxiliary `..._uncapped` variable is introduced when a later paragraph caps an earlier amount. — [ICFP 2021 paper, sections 3.3 and 3.4](https://arxiv.org/abs/2103.03198)
- [read directly] Formalising "a single sentence required us to explicitly declare otherwise implicit concepts, such as the definition of a year; and to clarify ambiguities, such as whether time periods may overlap"; Catala has no built-in year length, so "two years" must be written out (730 days under Reg. 1.121-1(c)(1)). — [ICFP 2021 paper, section 3.2](https://arxiv.org/abs/2103.03198)
- [read directly] Process: "this process is best achieved through pair-programming, in which a Catala expert transcribes a statute with the help of a legal expert"; "We do not expect lawyers to write Catala code by themselves." The interpreter's log shows "code positions coupled with the position inside the legal statute for each default logic definition taken". — [ICFP 2021 paper, sections 3.5, 6 and 7](https://arxiv.org/abs/2103.03198)
- [read directly] Current compiler: a law heading token is `LAW_HEADING (title, article_id, is_archive, precedence)`, parsed from a line of `#` characters, a title, an optional `| <article id>` and an optional `[archive]` marker; precedence is the number of `#`. Parser node kinds include `LawHeading`, `LawText`, `CodeBlock` (with `is_metadata` true or false) and `LawInclude` (legislative text file, PDF file with page, or Catala file). — [catala compiler/surface/lexer_common.ml](https://github.com/CatalaLang/catala/blob/f043039da3d3f5f598c3cf90afa30650af3558ad/compiler/surface/lexer_common.ml), [parser.mly](https://github.com/CatalaLang/catala/blob/f043039da3d3f5f598c3cf90afa30650af3558ad/compiler/surface/parser.mly)
- [read directly] The runtime `code_location` record has fields `filename`, `start_line`, `start_column`, `end_line`, `end_column`, `law_headings : string list`, so every evaluated definition carries its file span and the chain of headings above it. — [catala runtimes/ocaml/catala_runtime.mli](https://github.com/CatalaLang/catala/blob/f043039da3d3f5f598c3cf90afa30650af3558ad/runtimes/ocaml/catala_runtime.mli)
- [read directly] Current syntax cheat sheet shows scope variable kinds `input`, `output`, `internal`, `context` (and combinations `input output`, `context output`), multi-step variables with `state before` / `state after`, `label lbl1 definition var1 equals 0`, `exception lbl1 definition var1 equals 0`, unlabelled `exception definition`, date literals `|2024-04-01|`, and `date round down` / `date round up`. — [catala doc/syntax/syntax_en.catala_en](https://github.com/CatalaLang/catala/blob/f043039da3d3f5f598c3cf90afa30650af3558ad/doc/syntax/syntax_en.catala_en)

### Inferences
- The unit of correspondence the authors use is the paragraph (the smallest enumerated subdivision, e.g. (b)(2)(A)), and the granularity of traceability at run time is the heading chain plus line span, not a character span inside the paragraph. A span-level dictionary is finer than Catala's link.
- Catala's base-plus-exception tree maps directly onto provision relations a Colorado catalogue needs: "general rule", "exception to (label)", "cap on (variable)", "applicability condition". The `state before/after` device corresponds to "amount before limitation" and "amount after limitation".
- Catala has no parameter file: constants are definitions in scopes, and a dated change is a definition under a date condition. Effective dating is therefore a rule, not metadata (see section 6).

### Gaps
- I did not read the Catala book/tutorial or the French examples, so the practice for dated definitions and for the `| LEGIARTI...` article identifiers in real programs is not documented here; the `[archive]` flag's intended use is inferred from its name only.
- The ICFP paper predates the `input`/`output`/`internal` annotations (it calls them a planned "minor syntactic improvement"); the current syntax comes from the repository, not the paper.

## 4. FLINT / Calculemus (TNO): frame types, slots, link to source text

### Takeaway
FLINT represents an interpretation of a normative source as three kinds of frame (act, fact, duty); the act frame is the core and each frame is backed by one or more source references. I could read directly only a short arXiv case study; the slot names and the source-linking detail come from search summaries.

### Cited Findings
- [read directly] "A Flint frame consists of several fixed components, each to be assigned a value to create an instance of a frame. The language is limited to three classes of frames: acts, facts and duties." — [Lutz, "Deontic Paradoxes in Library Lending Regulations: A Case Study in Flint", arXiv 2212.05893](https://arxiv.org/abs/2212.05893)
- [read directly] "An act frame describes what some actor can do and what happens because of that action, given that some preconditions are satisfied. If these preconditions are complex (e.g. 'A OR B'), a fact frame can be used to explicitly give the (Boolean) formula for this complex fact and support this definition with one or more sources." — [arXiv 2212.05893](https://arxiv.org/abs/2212.05893)
- [read directly] "A duty frame describes some desirable or ideal course of action, by enumerating three acts: the act that creates the duty ..., the act that enforces the duty ..., and the act that terminates the duty". Duties concern acts only ("an ought-to-do language"); "duties and facts are created (made true) or terminated (made false) by an act." — [arXiv 2212.05893](https://arxiv.org/abs/2212.05893)
- [read directly] Purpose: FLINT was developed by Van Doesburg et al. "to capture and compare different interpretations of sources of norms"; ambiguity can lead "to more than one interpretation of the same source". — [arXiv 2212.05893](https://arxiv.org/abs/2212.05893)
- [search summary] Act frame slots: the action, the actor that performs it, the object acted upon, the recipient, a precondition, and creating and terminating effects; in the ontology form the properties are named `hasActor`, `hasRecipient`, `hasObject`, `hasAction`, `hasPrecondition`, `creates`, `terminates`. — [CEUR-WS Vol-3256 km4law1](https://ceur-ws.org/Vol-3256/km4law1.pdf), [IOS Press SSW230016](https://ebooks.iospress.nl/pdf/doi/10.3233/SSW230016)
- [search summary] Each frame has a source field: "a reference to the source of the act type, including information on version" (example citing a GDPR article). — [Jusletter IT 2020 guidelines article](https://author.weblaw.ch/magnoliaAuthor/jusletter-it/en/issues/2020/27-Mai-2020/5_2_guidelines_for_n_9663a714b4.html)
- [search summary] Calculemus is "a step-by-step guide for the interpretation and use of sources of norms" and FLINT the language for "normative states, and normative transitions"; the method recognises actions, duties, actors and facts from sentence structure and fills the frames "with text fragments extracted directly from the sentences". — [CEUR-WS Vol-3526 paper-03](https://ceur-ws.org/Vol-3526/paper-03.pdf), [TNO, Schoevers 2023](https://publications.tno.nl/publication/34643563/6TZNBhkx/schoevers-2023-extracting.pdf)
- [search summary] TNO (van Gessel and colleagues) is formalising FLINT; an executable relative, eFLINT, exists. — [TNO, van Gessel 2025](https://publications.tno.nl/publication/34644760/s7fKr0zP/gessel-2025-formalizing.pdf), [arXiv 2511.12276](https://arxiv.org/abs/2511.12276)

### Inferences
- FLINT fills slots with text fragments taken from the sentence, which is the same move as a span extraction: slot = role label, value = verbatim span, plus a versioned source reference. That is the closest precedent among these systems for a span dictionary.
- FLINT is built for powers, duties and state changes (who may do what to whom), not arithmetic. For income tax its fit is the procedural provisions (the taxpayer must file, the department sets the rate or refund tiers, the controller certifies the surplus); amounts and rates sit in fact frames or outside the model.

### Gaps
- No FLINT/Calculemus specification or repository was read directly. The exact slot list, whether a duty frame has named slots beyond the three acts (for example duty holder and claimant), and the exact structure of the source reference (document, article, version, text offsets) are unverified.
- I found no direct evidence on whether FLINT sources point to character offsets or only to article-level citations plus the copied fragment.

## 6. Cross-cutting conventions: effective dating, uncertainty and provisional values, overrides by later instruments or agencies

### Takeaway
Effective dating is uniform in the OpenFisca family (a value holds from its start date until the next one; `null` ends it) and is a rule condition in Catala. None of the systems read has a structured field for provisional status, for which instrument set a value, or for an agency value that departs from the statute; PolicyEngine records all three in YAML comments and description prose, and OpenFisca's `expected` key is ignored by the engine.

### Cited Findings

**Effective dating**
- [read directly] OpenFisca: values are keyed by start date; in the documented example the parameter is "undefined before 1993", "equal to 1000 from 1993 to 2010", and so on; "The ordering of the dates has no effect." — [openfisca-doc legislation_parameters.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/legislation_parameters.md)
- [read directly] Ending a parameter: "We can end `housing_allowance` at a specific date by simply assigning `null` as a value for that date"; the same for a scale by assigning `null` across all brackets. — [openfisca-doc 40_legislation_evolutions.md](https://github.com/openfisca/openfisca-doc/blob/35577e3c38b3439695df77dde859ea21a7c99125/source/coding-the-legislation/40_legislation_evolutions.md)

- [read directly] OpenFisca documents `expected:` in place of `value:` for an anticipated figure (`2020-01-01: expected: 1700`, "expected to be raised to 1700"). ### Inferences
- Fields that every system here leaves to comments, and that a Colorado dictionary could make explicit: `set_by` (statute, constitutional limit, ballot measure, agency determination, forecast), `status` (enacted, certified, published on form, projected, unknown), `trigger` (the condition on which the value depends, with its own citation), `supersedes` / `overridden_by`, per-value source rather than per-parameter source, and a conflict note where sources disagree. This project's existing `conflict_note` and refuse-to-compute rule already go further than PolicyEngine on the last two.
- PolicyEngine's practice of storing projected values as real values, and of carrying the last value forward indefinitely, is the opposite of this project's rule that an unknown value stays unrecorded so the engine refuses to compute. OpenFisca's inert `expected` key is the closer precedent: record the anticipated figure where the engine cannot use it.
- The start-date-only model cannot say "this value is known to apply through tax year N and is unknown after". An explicit end date or a `null` after the last verified year is needed to stop carry-forward.
- "Rate on the form" versus "rate in the statute" are two different parameters in substance (base rate in C.R.S. 39-22-104 and a temporary TABOR reduction); PolicyEngine merges them into one series. A provision-type catalogue should keep a "temporary rate reduction / refund mechanism" type separate from "rate imposition".

### Gaps
- I found no convention in any of these systems for recording confidence or verification status of a value as structured data, and no evidence that one exists; this is absence in the files read, not a confirmed absence across the projects.
- How Catala programs in practice encode dated values (for example conditions on a current-date variable) was not read from real examples.
- FLINT's handling of versions of a source over time rests on one search-summary phrase ("including information on version").
- Better Rules and OECD positions on effective dating and provisional values were not retrievable.
