# Element and concept vocabularies of legal markup standards (raw material for a tax-statute span dictionary)

Evidence labels used below: **[read directly]** = I read the schema, ontology file, user guide or paper text in this session (cloned from GitHub or downloaded from arxiv.org). **[search summary]** = from a web-search result summary only; treat as a lead. **[recall, unverified]** = names I remember from the specification but could not read in this session (docs.oasis-open.org was refused); do not rely on these without checking.

Files read: USLM `USLM-User-Guide.md`, `USLM.xsd` (1.0) and `uslm-components-2.1.0.xsd`; Akoma Ntoso `akomantoso30.xsd` from the folder `TemporaryRelease20170330Final` of the OASIS GitHub repository (a repository release, which I did not compare against the final OASIS Standard) and its bundled examples; LKIF Core `.ttl` modules; the DAPRECO GDPR knowledge base in LegalRuleML; arXiv 1711.06128, 2209.05090, 2211.12752, 2001.11245, 2506.08899.

## 1. Exact element or class names per standard, for categories (a) to (h)

### Takeaway
USLM and Akoma Ntoso name document structure richly and name content semantics thinly: both have only a handful of inline elements (term/def, ref, date, and in Akoma Ntoso `quantity`), and neither has an element for rate, threshold, base, exception or addressee. Party, condition and normative effect are named only in the rule/ontology layer (LegalRuleML, LKIF) and in annotation schemes from requirements engineering and NLP.

### Cited Findings

**USLM** [read directly]
- (a) Structure. Abstract element `<level>`, with concrete levels derived from it: `<title>`, `<subtitle>`, `<chapter>`, `<subchapter>`, `<part>`, `<subpart>`, `<division>`, `<subdivision>`, `<article>`, `<subarticle>`, `<section>`, `<subsection>`, `<paragraph>`, `<subparagraph>`, `<clause>`, `<subclause>`, `<item>`, `<subitem>`, `<subsubitem>`, plus `<preliminary>`. A level is "(1) a `<num>` identification designation, (2) an optional `<heading>`, and (3) either primarily textual `<content>`, lower hierarchical `<level>` children, or a few other possible elements". "Big levels" are above `<section>`, "small levels" below. Text blocks: `<text>`, `<chapeau>`, `<continuation>`, `<proviso>`, `<content>`, `<p>`. — [USLM User Guide §4.3, §6.5, §6.6, §9](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- (b) Time. Inline `<date>` with normalized `@date`, or `@beginDate`/`@endDate` for a range (the 2.1.0 schema declares and documents `@startDate` and `@endDate` instead; the user guide and the schema disagree on the attribute name). Versioning attributes `@startPeriod`, `@endPeriod`, `@status`, `@partial`. `@status` values: `proposed`, `withdrawn`, `cancelled`, `pending`, `operational`, `suspended`, `renumbered`, `repealed`, `expired`, `terminated`, `hadItsEffect`, `omitted`, `notAdopted`, `transferred`, `redesignated`, `reserved`, `vacant`, `crossReference`, `unknown`. Amendment `<action>` carries `@commencementDate`. Note element `<effectiveDateNote>` ("a note to indicate the effectivity of a provision"). — [USLM User Guide §4.5.6, §4.5.10, §4.5.11, §7.4](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md); [uslm-components-2.1.0.xsd](https://github.com/usgpo/uslm/blob/main/uslm-components-2.1.0.xsd)
- (c) Quantities. No dedicated amount/quantity/rate element appears in the element lists of `USLM.xsd` or `uslm-components-2.1.0.xsd`. The only hook is the generic "Value" attribute group: `@value`, `@startValue`, `@endValue` ("normalized values computed from the text content"). — [USLM User Guide §4.5.9](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- (d) Definitions. `<def>` (USLM 1.0: "One or more `<term>` elements, as well as their respective definitions") and inline `<term>` ("a word or phrase that is being defined"; the containing element "has a `@role="definitions"`"). `<def>` is in `USLM.xsd` but is not declared as an element in `uslm-components-2.1.0.xsd`, which only mentions it in a comment; `<term>` is in both. — [USLM.xsd](https://github.com/usgpo/uslm/blob/main/USLM.xsd); [uslm-components-2.1.0.xsd](https://github.com/usgpo/uslm/blob/main/uslm-components-2.1.0.xsd)
- (e) Cross-references. `<ref>` with `@href` (a path resolved by a resolver), `@idref`, `@portion`; 2.1.0 adds inline `<qualifier>` ("to add a qualifier to a reference, such as the 'as amended by' language"). — [USLM User Guide §4.5.5](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- (f) Conditions and exceptions. Only `<proviso>`: "A paragraph of text, usually beginning with 'Provided that' or 'Provided', that states conditions on the law to which it is related". No element for "except", "unless", "notwithstanding" or "if". — [USLM User Guide §6.6, §9.4](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- (g) Party and (h) normative effect. No element. The closest is the 2.1.0 generic inline `<entity>` ("to identify a text fragment introducing or referring to an ontological concept. This is modelled after the Akoma Ntoso `<entity>` element", distinguished by `@role`). — [uslm-components-2.1.0.xsd](https://github.com/usgpo/uslm/blob/main/uslm-components-2.1.0.xsd)
- Provenance. Notes: `<sourceCredit>` ("to indicate the source of a provision"), `<statutoryNote>`, `<editorialNote>`, `<changeNote>`, `<uscNote>`; note `@type` values inline, endnote, footnote, uscNote; `@topic` (e.g. `@topic="regulations construction"`). — [USLM User Guide §14](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)

**Akoma Ntoso** [read directly, schema `akomantoso30.xsd`]
- (a) Structure. Hierarchical containers (complex type `hierarchy`): `clause`, `section`, `part`, `paragraph`, `chapter`, `title`, `book`, `tome`, `article`, `division`, `list`, `point`, `indent`, `alinea`, `rule`, `subrule`, `proviso`, `subsection`, `subpart`, `subparagraph`, `subchapter`, `subtitle`, `subdivision`, `subclause`, `sublist`, `level`, `transitional`, and the generic `hcontainer` (required `name` attribute). Children of a `hierarchy`: `num`, `heading`, `subheading`, then `intro`, lower containers, `wrapUp`, or else `content`. Block lists: `blockList` with `listIntroduction`, `item`, `listWrapUp`. — [akomantoso30.xsd](https://github.com/oasis-open/legaldocml-akomantoso/blob/master/TemporaryRelease20170330Final/akomantoso30.xsd)
- (b) Time. Inline `date` (attribute `date`) and `time`; metadata `lifecycle` > `eventRef` (attributes `date`, `source`, `refersTo`, `type` with values `generation`, `amendment`, `repeal`); `temporalData` > `temporalGroup` > `timeInterval` (`start`, `end`, `duration`, required `refersTo`); attribute `period` on content; attribute `status` (values `removed`, `temporarilyRemoved`, `translated`, `editorial`, `edited`, `verbatim`, `incomplete`, `unknown`, `undefined`, `ignored`). — same schema
- (c) Quantities. Inline `quantity`: "to identify a text fragment introducing or referring to a quantity. This could be a dimensionless number, or a number referring to a length, weight, duration, etc. or even a sum of money. The attribute normalized contains the value normalized in a number, if appropriate." Attribute: `normalized`. No unit, currency or percent attribute is declared in that attribute group. — same schema
- (d) Definitions. Inline `def` ("used for the definition of a term used in the rest of the document") and inline `term` ("a text fragment introducing or referring to a term in the ontology"), resolved through metadata `TLCTerm`. — same schema
- (e) Cross-references. `ref` ("an inline element containing a legal reference"), `mref` (multiple references), `rref` (range, attributes `from` and `upTo`). — same schema
- (f) Conditions and exceptions. In the text: only the container `proviso` ("a hierarchical container called 'proviso' either explicitly or due to the local tradition"). In metadata (`analysis`): `scopeMod` with `type` values `exceptionOfScope`, `extensionOfScope`; `condition` ("an open set of conditions on the modification (non managed by Akoma Ntoso)"); `domain`. — same schema
- (g) Party. Inline `person`, `organization`, `role`, `concept`, `object`, `event`, `location`, `process`, generic `entity`; each points with `refersTo` to a `TLCPerson`, `TLCOrganization`, `TLCRole`, `TLCConcept` etc. These mark a mention; they do not say the party is the addressee of a rule. — same schema
- (h) Normative effect. No obligation/permission/right element. The `analysis` block classifies modifications only: `textualMod` (`repeal`, `substitution`, `insertion`, `replacement`, `renumbering`, `split`, `join`), `meaningMod` (`variation`, `termModification`, `authenticInterpretation`), `scopeMod`, `forceMod`, `efficacyMod`, `legalSystemMod`. — same schema

**LegalRuleML** (rule layer, not text markup)
- Statement types: normative statements `<lrml:ConstitutiveStatement>`, `<lrml:PrescriptiveStatement>`; `<lrml:FactualStatement>`; `<lrml:OverrideStatement>`; violation-reparation statements `<lrml:PenaltyStatement>`, `<lrml:ReparationStatement>`. [read directly] — [Lam & Hashmi, arXiv 1711.06128](https://arxiv.org/abs/1711.06128)
- (f) Conditions: RuleML `<ruleml:Rule>` with `<ruleml:if>` and `<ruleml:then>`, atoms `<ruleml:Atom>` with `<ruleml:Rel iri=...>`, `<ruleml:Var>`, `<ruleml:Ind>`; connectives `<ruleml:And>`, `<ruleml:Or>`. [read directly] — [DAPRECO KB](https://github.com/dapreco/daprecokb/blob/master/gdpr/rioKB_GDPR.xml); [notes with Lam et al. example](https://github.com/inariksit/cclaw-zettelkasten/blob/master/legalruleml.md)
- (g) Party: `<lrml:Bearer>` node on a deontic operator. [read directly] — [Steen & Fuenmayor, arXiv 2209.05090](https://arxiv.org/abs/2209.05090). "The participants may be designated as agents, bearers or third parties, who may have roles and be part of an authority." [read directly, secondary description] — [Sleimi et al., arXiv 2001.11245](https://arxiv.org/abs/2001.11245). An obligation is "a deontic specification that a Bearer is legally bound to meet, with a Violation if it isn't met" [search summary of the OASIS glossary].
- (h) Normative effect: deontic elements `<lrml:Obligation>`, `<lrml:Permission>`, `<lrml:Prohibition>`, `<lrml:Right>`; also `<lrml:Violation>`, `<lrml:Compliance>`, `<lrml:Reparation>`, `<lrml:SuborderList>`. "the element 'right' is a deontic specification that gives a permission to a party and implies that there is no obligation or prohibition on the other parties". [read directly] — [arXiv 1711.06128](https://arxiv.org/abs/1711.06128)
- (d) Definitions: constitutive statements "represent institutional facts and provide definitions of terms". (b), (e): see sections 3 and 4.

**LKIF Core** (OWL ontology; class names read from the `.ttl` modules) [read directly] — [github.com/RinkeHoekstra/lkif-core](https://github.com/RinkeHoekstra/lkif-core)

- Legal sources (`norm` module): `Legal_Source`, `Legal_Document`, `Statute`, `Regulation`, `Code`, `Decree`, `Directive`, `Treaty`, `Precedent`, `Soft_Law`, `Legal_Doctrine`.
- (g) Party: `action:Agent`, `action:Person`, `action:Organisation`, property `action:actor`; `role:Role`, `Person_Role`, `Organisation_Role`, `Social_Role`, properties `plays`, `played_by`; `legal-role:Legal_Role`; `legal-action:Legal_Person`, `Natural_Person`, `Public_Body`; `expression:addressee`, `expression:bears`.
- (f) `expression:Exception`, `expression:Qualification`; `lkif-rules:Rule`, `Valid_Rule`, `Exception`, `Assumption`, properties `applies`, `excluded`, `prior`, `rebuts`.
- (b) `time`: `Interval`, `Moment`, Allen relations (`before`, `after`, `during`, `overlap`, `starts`, `finishes`). `time-modification`: `Enter_in_Force_Date`, `Start_in_Force`, `End_in_Force`, `In_Force_Interval`, `Start_Efficacy`, `End_efficacy`, `Efficacy_Interval`, `Application_Date`, `Application_Interval`, `Publication_Date`, `Existence_Date`, `Retroactivity`, `Ultractivity`, `Suspension`, `Repeal`, `Prorogation_in_Force`, `Prorogation_Efficacy`; properties `in_force`, `efficacy`, `application`, `initial_date`, `final_date`.
- (c) No quantity, amount or rate class appeared in the modules I listed (norm, legal-action, legal-role, expression, time, role, action, lkif-rules, time-modification).

**Phrase-level annotation scheme reconciling the above** [read directly] — [Sleimi et al., arXiv 2001.11245](https://arxiv.org/abs/2001.11245)
- Phrase-level concepts with glossary: Action, Actor, Agent ("the main actor performing the action"), Target ("an entity that is directly affected by an action"), Auxiliary Party, Artifact, Situation, Condition ("a constraint stating the properties that must be met"), Constraint ("a restriction placed on the applicability of a legal provision"), Exception ("a constraint indicating that a legal provision takes precedence over another legal provision"), Modality ("a verb indicating the modality of the action (e.g may, must, shall)"), Reference, Time ("the moment or duration associated with the occurence of an action"), Location, Reason, Result, Sanction, Violation. Statement-level: Definition, Fact, Obligation, Permission, Prohibition, Penalty.

### Inferences
- A span dictionary for numeric tax rules can borrow established names for structure (`chapeau`/`intro`, `continuation`/`wrapUp`, `proviso`), for defined terms (`term`, `def`), for references (`ref`), for dates (`date`), for amounts (`quantity` with a normalized value), for the party (`Bearer`; "agent" and "target" in Sleimi et al.), for the effect (`Obligation`, `Permission`, `Prohibition`, `Right`), and for limits on applicability (Condition, Constraint, Exception). "Rate", "threshold", "base" and "tax years covered" have no element in any of the five; they would be project-defined subtypes of `quantity` and of a temporal constraint.
- A tax credit fits LegalRuleML `Right` or LKIF `Right`/`Liability_Right` loosely; none of the sources read discusses credits or entitlements to money, so that mapping is my interpretation.

## 2. Lead-in sentences completed by list items, and provisos or exceptions

### Takeaway
Both text standards give the lead-in its own element, sibling to the items it introduces (`chapeau` in USLM, `intro` in Akoma Ntoso), and both give trailing text its own element (`continuation`, `wrapUp`). The only exception-like construct either marks in the text is the "Provided that" proviso; ordinary "except"/"unless" language is left as plain text.

### Cited Findings
- USLM: "Sandwich structures are hierarchical levels that start and/or end with text rather than lower levels... The `<chapeau>` (French for 'hat') and `<continuation>` elements are provided for this structure. The `<chapeau>` precedes the lower levels and the `<continuation>` follows the lower levels. The `<continuation>` element can also be used for cases where interstitial text is found between elements of the same level." [read directly] — [USLM User Guide §9.4](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- USLM: "One specific type of continuation text is a paragraph-like structure beginning with 'Provided that' or 'Provided'. The `<proviso>` element is used in this case. Multiple provisos may exist." The 2.1.0 schema adds "or 'Provided further'" and says a proviso "can contain their own complex structure including sandwich structures". `<chapeau>`, `<continuation>` and `<proviso>` all derive from `<text>`. [read directly] — [uslm-components-2.1.0.xsd](https://github.com/usgpo/uslm/blob/main/uslm-components-2.1.0.xsd)
- Akoma Ntoso: `intro` is "a heading element in a hierarchy that contains paragraphs introducing one or more lower hierarchical elements"; `wrapUp` is "a concluding element in a hierarchy that contains paragraphs wrapping up the preceding lower hierarchical elements"; `content` is "the final container in a hierarchy". Inside a `blockList`: `listIntroduction` ("before any item of the list") and `listWrapUp` ("after all items"). [read directly] — [akomantoso30.xsd](https://github.com/oasis-open/legaldocml-akomantoso/blob/master/TemporaryRelease20170330Final/akomantoso30.xsd)
- Akoma Ntoso `proviso` is a full hierarchical container (type `hierarchy`), so unlike USLM's it can carry `num`, `heading`, `intro` and nested levels. [read directly] — same schema
- Akoma Ntoso has no interstitial-text element equivalent to USLM's mid-list `<continuation>` among the children of `hierarchy` that I listed (`intro`, `componentRef`, `crossHeading`, `wrapUp`, `content` plus the containers). [read directly] — same schema
- Exceptions in the rule layer: LKIF `expression:Exception` and `lkif-rules:Exception`; Sleimi et al. distinguish Condition, Constraint and Exception at phrase level. [read directly] — [lkif-core](https://github.com/RinkeHoekstra/lkif-core); [arXiv 2001.11245](https://arxiv.org/abs/2001.11245)

### Inferences
- For span extraction, the lead-in matters because a parameter's meaning can be split between the chapeau ("the tax is imposed at the rate of") and an item ("4.4 percent for tax years ..."). The standards' practice supports recording the chapeau as a separate, addressable unit and letting a span cite both.
- An "exception" span class has precedent only at the proviso level in text markup; a finer class (exception vs. condition vs. constraint) follows Sleimi et al., not USLM or Akoma Ntoso.

### Gaps
- I did not find a worked Akoma Ntoso example of `proviso`: none of the nine bundled example files uses it.

## 3. How Akoma Ntoso and LegalRuleML model time

### Takeaway
Akoma Ntoso separates events from intervals and intervals from their meaning: dated events live in `lifecycle`, intervals in `temporalGroup`/`timeInterval` point to those events and say via `refersTo` which kind of interval they are, and content points to a group with `period`. Force, efficacy and application are distinct named periods. This is the closest established model for "applies to tax years beginning on or after X".

### Cited Findings
- `eventRef`: "specifying facts about an event that had an effect on the document. For each event, a date, a type and a document that generated the event must be referenced." Types: `generation`, `amendment`, `repeal`. [read directly] — [akomantoso30.xsd](https://github.com/oasis-open/legaldocml-akomantoso/blob/master/TemporaryRelease20170330Final/akomantoso30.xsd)
- `timeInterval`: "built either with two dates or with a date and a duration (exactly two of the 'start', 'end' and 'duration' attributes can be specified). Values of the 'start' and 'end' attributes are NOT dates, but references to event elements in the corresponding metadata section. The refers attribute is a reference to a temporal concept belonging to the Akoma Ntoso ontology". [read directly] — same schema
- `period` attribute: "used in versioned content and metadata elements to indicate a time interval in which they were in force, in efficacy, or in any other type of interval as specified in the corresponding temporalGroup." [read directly] — same schema
- Modifications carry four separate period children: `force`, `efficacy`, `application`, `duration` (each of `periodType`), plus `condition`. `forceMod` types: `entryIntoForce`, `endOfEnactment`, `postponementOfEntryIntoForce`, `prorogationOfForce`, `reEnactment`, `unconstitutionality`. `efficacyMod` types: `entryIntoEfficacy`, `endOfEfficacy`, `inapplication`, `retroactivity`, `extraefficacy`, `postponementOfEfficacy`, `prorogationOfEfficacy`. `legalSystemMod` includes `expiration`. [read directly] — same schema
- Point-in-time versions are FRBR expressions: `FRBRWork`, `FRBRExpression`, `FRBRManifestation`, each with `FRBRthis`, `FRBRuri`, `FRBRdate`. An expression IRI in the DAPRECO file reads `/akn/eu/act/regulation/2018-05-25/eng@2018-05-25/!main#`. [read directly] — same schema; [DAPRECO KB](https://github.com/dapreco/daprecokb/blob/master/gdpr/rioKB_GDPR.xml)
- Example usage: the bundled UK act uses `period="eRef_1"` 15 times with `eventRef` entries `refersTo="#DateOfEnactment"` (2014-07-17) and `refersTo="#DateOfRepeal"` (2016-12-31). [read directly] — [uk_pga-2014-27-enacted-data.xml](https://github.com/oasis-open/legaldocml-akomantoso/tree/master/csprd02-part2-specs/csprd02-part2-specs-examples)
- LKIF's `time-modification` module names the same three axes: `In_Force_Interval`, `Efficacy_Interval`, `Application_Interval`, with `Retroactivity` and `Ultractivity`. [read directly] — [lkif-core](https://github.com/RinkeHoekstra/lkif-core)
- USLM, by contrast, has one axis: `@startPeriod`/`@endPeriod` on a version, and the guide warns they "may not correspond to an effective date or repeal date". [read directly] — [USLM User Guide §7.4](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- LegalRuleML: the metadata part holds "the temporal information about the legal sources and the document itself", and context exists because "the same rule can be interpreted differently due to a variety of parameters such as jurisdiction and temporal parameters that can be changed over time". [read directly] — [arXiv 1711.06128](https://arxiv.org/abs/1711.06128)
- LegalRuleML: an OASIS issue (LEGALRULEML-2) says the `Efficacious` and `InForce` IRIs in the vocab namespace are used in examples but have no definition in the documentation or in a formal ontology. [search summary] — [issues.oasis-open.org/browse/LEGALRULEML-2](https://issues.oasis-open.org/browse/LEGALRULEML-2)

### Inferences
- A tax-year span ("for income tax years commencing on or after January 1, 2022") is an application period in Akoma Ntoso terms, distinct from the date the amending act took force. A span class for "tax years covered" should be kept separate from "effective date of the provision" and from "repeal/sunset date"; the standards give precedent for exactly that three-way split (force, efficacy, application).
- None of the standards has a notion of a fiscal or tax year as a unit; intervals are between dated events.

### Gaps
- LegalRuleML's temporal element names were not read. From recall, unverified: `lrml:TimeInstants`, `lrml:TemporalCharacteristics`, `lrml:TemporalCharacteristic` with `lrml:forStatus`, `lrml:hasStatusDevelopment`, `lrml:atTimeInstant`, linked to statements by `lrml:appliesTemporalCharacteristics` in a `lrml:Context`. A search for these names returned no confirming text.
- The precise definitions of "force", "efficacy" and "application" are not in the schema comments; they are in the Akoma Ntoso specification prose, which I could not fetch.

## 4. How LegalRuleML separates text from rule; constitutive vs prescriptive; defeasibility and overriding

### Takeaway
LegalRuleML keeps rules and sources in separate blocks and joins them with `Association` records (`appliesSource` to `toTarget`), so one source can back many rules and one rule many sources. Rule conflict is handled by rule strength plus explicit `Override` pairs. This is direct precedent for recording "source A overrides source B" as a first-class relation instead of silently picking one.

### Cited Findings
- Document shape: "three main components namely: metadata, context and statements". [read directly] — [arXiv 1711.06128](https://arxiv.org/abs/1711.06128)
- Source linking as used in practice: `<lrml:LegalReferences type="legislative">` holding `<lrml:LegalReference refersTo="gdprC2A5P1p1ref" refID="GDPR:art_5__para_1__content__list_1__point_a"/>` (the `refID` is an Akoma Ntoso element id under a `<lrml:Prefix>`), then `<lrml:Associations><lrml:Association><lrml:appliesSource keyref="#gdprC2A5P1p1ref"/><lrml:toTarget keyref="#statements1"/></lrml:Association>`. Rules are grouped in `<lrml:Statements key=...>`; `<lrml:Context type=...>` with `<lrml:inScope keyref=...>` attaches properties to statements. [read directly] — [DAPRECO KB](https://github.com/dapreco/daprecokb/blob/master/gdpr/rioKB_GDPR.xml)
- Constitutive vs prescriptive: constitutive norms are "used to represent institutional facts and provide definitions of terms"; prescriptive norms "specify the deontic behavior and effects". "the head of a prescriptive statement is a list of deontic formulas"; in the authors' translation a constitutive statement becomes a strict rule and a prescriptive statement a defeasible rule. [read directly] — [arXiv 1711.06128](https://arxiv.org/abs/1711.06128)
- Strength: `<lrml:hasStrength><lrml:DefeasibleStrength key="str1" iri=.../></lrml:hasStrength>` inside the rule. [read directly] — same paper
- Override: `<lrml:OverrideStatement><lrml:Override over="#r2" under="#r1"/></lrml:OverrideStatement>` "defines the relationship of superiority such that the conclusion of r2 overrides the conclusion of r1"; in defeasible logic terms r2 > r1. [read directly] — same paper
- Penalties: `<lrml:ReparationStatement>` > `<lrml:Reparation>` with `<lrml:appliesPenalty keyref=.../>` and `<lrml:toPrescriptiveStatement keyref=.../>`; `<lrml:PenaltyStatement>` holds a `<lrml:SuborderList>`. [read directly] — same paper
- Refining a deontic element: by an `iri` attribute or with `<lrml:Association>` and `<lrml:toTag>`; `<lrml:appliesModality>` appears in associations. [read directly] — same paper; DAPRECO KB
- LKIF's rule module has the same idea under other names: `Rule`, `Exception`, `Assumption`, and properties `prior`, `rebuts`, `excluded`, `applies`. [read directly] — [lkif-core](https://github.com/RinkeHoekstra/lkif-core)
- Akoma Ntoso has judicial-analysis relations between documents (`supports`, `isAnalogTo`, `applies`, `extends`, `restricts`, `derogates`, `contrasts`, `overrules`, `dissentsFrom`, `putsInQuestion`, `distinguishes`) inside `judicial`. [read directly] — [akomantoso30.xsd](https://github.com/oasis-open/legaldocml-akomantoso/blob/master/TemporaryRelease20170330Final/akomantoso30.xsd)

### Inferences
- The project's `conflict_note` on a parameter is an informal `Override`. A structured form would name the prevailing source, the overridden source and the ground, mirroring `over`/`under`.
- Span-level grounding (exact text spans per parameter) is finer than LegalRuleML's source linking in the one large public knowledge base, where the target is a provision id (article, paragraph, point), not a character span.
- "derogates" and "restricts" are the Akoma Ntoso names nearest to "one provision carves out from another"; they are declared for judgments, so reusing them for statute-to-statute relations would be an extension.

### Gaps
- `lrml:LegalSources`/`lrml:LegalSource` with `sameAs`, and `lrml:Alternatives` (several formalisations of one text), are recalled but were not read or seen in any file this session; the DAPRECO file uses `LegalReferences`/`LegalReference` instead.
- I found no LegalRuleML example of a tax or numeric rule other than the "5% surcharge" contract rule in Lam & Hashmi, which encodes the surcharge as an atom with no numeric value.

## 5. Label sets and inter-annotator agreement in deontic and Hohfeldian annotation

### Takeaway
Label sets cluster around obligation, permission, prohibition, with right/entitlement and power added in some schemes; full eight-term Hohfeldian annotation of statutes with reported agreement was not found. Reported agreement ranges from Krippendorff's alpha 0.65 for sentence-level deontic type to Cohen's kappa above 0.8 for phrase-level metadata, and agreement on full rule formalisation is far lower.

### Cited Findings
- Hohfeld's eight positions: "right, privilege, power, immunity, duty, no-right, liability, and disability", each paired with one opposite and one correlative. [read directly, secondary] — [Sleimi et al., arXiv 2001.11245](https://arxiv.org/abs/2001.11245)
- Sleimi et al. (Luxembourg legislation, 18 phrase-level and 6 statement-level types listed in section 1): Cohen's kappa 0.824 in the qualitative study on traffic-law statements, and 0.815 and 0.813 in the evaluation case studies, each described as "almost perfect agreement". Disagreement counting: differing annotations "counted as disagreements". [read directly] — [arXiv 2001.11245](https://arxiv.org/abs/2001.11245)
- Sancheti et al. (LexDeMod, lease contracts, agent-specific): labels Obligation, Entitlement, Prohibition, Permission, No Obligation, No Entitlement, plus None; annotators also select the modal trigger span. Average Krippendorff's alpha 0.65 for deontic type and 0.71 token-level for trigger spans; "'Shall' constitutes 44.6% of the annotated triggers" and expresses several types. 17.3% of sentences have multiple trigger annotations. [read directly] — [arXiv 2211.12752](https://arxiv.org/abs/2211.12752)
- Minkova et al. (NLLP 2023, EU legislation): three law-student annotators; labels 'Obligation', 'Permission', 'Power', 'Prohibition', 'Right', or no annotation. Agreement figures not seen. [search summary] — [aclanthology.org/2023.nllp-1.15](https://aclanthology.org/2023.nllp-1.15)
- "Deciphering disagreement in the annotation of EU legislation" (Artificial Intelligence and Law, 2024): agreement measured on nine tasks including deontic clauses and active and passive roles, at two stages; a Krippendorff's alpha "not exceeding .78" is mentioned without the label or stage. [search summary, unverified] — [doi 10.1007/s10506-024-09423-9](https://link.springer.com/article/10.1007/s10506-024-09423-9)
- Braun (2023) review of 29 legal annotation publications, as cited by that paper: average Cohen's kappa .76, Fleiss' kappa .675, Krippendorff's alpha .677; annotation process explanations "missing or at best limited". [search summary] — same link
- Waltl et al. (German Civil Code tenancy law, n = 601): taxonomy of nine functional norm types such as duties, prohibitions, permissions. Full list and agreement not seen. [search summary] — [doi 10.1007/s10506-018-9228-y](https://link.springer.com/10.1007/s10506-018-9228-y)
- Peters and Wyner, "Legal Text Interpretation: Identifying Hohfeldian Relations from Text": assigns Hohfeldian duty relations with GATE; no kappa found. [search summary] — [abdn.elsevierpure.com record](https://abdn.elsevierpure.com/en/publications/legal-text-interpretation-identifying-hohfeldian-relations-from-t/)
- Agreement on full formalisation is much lower: three experienced coders encoding Australian Copyright Act provisions in defeasible deontic logic agreed on 0% of rules by perfect match in phase one; after agreeing a common term list, rule similarity was 10% to 30% (full correspondence) and 26% to 53% (semantic correspondence). [read directly, reported as prior work] — [arXiv 2506.08899](https://arxiv.org/abs/2506.08899)
- arXiv 2604.23585 is said to report Fleiss' kappa 0.84 overall and 0.89 for a four-label deontic classification (obligation, permission, prohibition, recommendation). [search summary, unverified]

### Inferences
- Agreement falls as the unit grows from phrase type, to sentence modality, to whole rule. That favours a dictionary of small, text-anchored span classes over asking annotators (or a model) for a full rule.
- Schemes that tie the label to a party ("agent-specific") and to a trigger span report usable agreement; this supports pairing an "effect" span with a "who it applies to" span.
- "Entitlement" (Sancheti et al.) is the label nearest to a tax credit among the schemes found.

### Gaps
- No study found that annotates tax statutes with deontic or Hohfeldian labels, and none that reports agreement for numeric spans (rates, thresholds).
- Per-label agreement tables (Sancheti Table 7; the EU legislation study) were not extracted.
- Springer and ACL Anthology pages could not be fetched; four of the items above rest on search summaries.

## 6. Which distinctions are widely adopted and which are rarely used

### Takeaway
Structural hierarchy, lead-in/continuation, references, defined terms and dates are used throughout the published examples; inline quantities, provisos in Akoma Ntoso, the efficacy/application axes and LegalRuleML's prescriptive and deontic elements are thinly used in the material I could inspect. Evidence here is limited to bundled examples and one knowledge base.

### Cited Findings
- USLM is the published format for the United States Code and for bill versions; the repository carries schema versions 1.0 through 2.1.0 and September 2024 bill-version samples. Across all files in the September 2024 bill-version sample folder, `<chapeau` occurs 3,058 times, `<term` 756 times and `<continuation` 178 times; there is no `<quantity` or `<amount` tag. `<proviso` occurs 1,990 times but in only 2 of the 14 lowercase-extension `.xml` samples (I did not check which bills; provisos are typical of appropriations text). [read directly] — [github.com/usgpo/uslm](https://github.com/usgpo/uslm)
- USLM states it "is designed to be consistent with Akoma Ntoso to the extent practicable. Many of the element and attribute names in USLM match the Akoma Ntoso equivalents", while not being a derivative or subset. [read directly] — [USLM User Guide §1.7](https://github.com/usgpo/uslm/blob/main/USLM-User-Guide.md)
- In the nine Akoma Ntoso example files bundled with the specification: `intro` appears in six files (15 times in the UK act, 11 in the EU proposal); `wrapUp` twice (UK act only); `term` 49 times and `def` 12 times in the EU proposal, `def` 4 times in the US act; `quantity` only in the two parliamentary debate examples (5 and 4 times), never in an act or bill; `proviso` not at all; `period` only in the UK act. [read directly] — [csprd02 examples](https://github.com/oasis-open/legaldocml-akomantoso/tree/master/csprd02-part2-specs/csprd02-part2-specs-examples)
- The largest public LegalRuleML knowledge base I inspected (DAPRECO, GDPR) contains 966 `lrml:ConstitutiveStatement` and no `lrml:PrescriptiveStatement`, `lrml:Obligation`, `lrml:Bearer` or `lrml:Override` elements; it records obligation vs permission as a `type` on `lrml:Context` (`rioOnto:obligationRule`, `rioOnto:permissionRule`) and has 276 `lrml:Association` records. [read directly] — [DAPRECO KB](https://github.com/dapreco/daprecokb/blob/master/gdpr/rioKB_GDPR.xml)
- The OASIS LegalRuleML examples repository has one use case; the others are placeholders ("Use Case #2: The use case serialises..."). [read directly] — [github.com/oasis-tcs/legalruleml](https://github.com/oasis-tcs/legalruleml)
- LegalRuleML Core 1.0 became an OASIS Standard in 2021. [search summary] — [oasis-open.org announcement](https://www.oasis-open.org/?p=7649)
- A user validating a sample against the compact LegalRuleML XSD got a validation error (mailing-list thread). [search summary] — [lists.oasis-open.org](https://lists.oasis-open.org/archives/legalruleml/202012/msg00000.html)
- Sleimi et al. derive 20 of 24 concepts from two requirements-engineering sources and note that "only few strands of work are concerned with definition, violation, penalty or sanction". [read directly] — [arXiv 2001.11245](https://arxiv.org/abs/2001.11245)

### Inferences
- Safe to ground in established practice: section/subsection/paragraph hierarchy, chapeau/intro and continuation/wrapUp, proviso (US usage, concentrated in a few bills), term/def, ref, date, the obligation/permission/prohibition/right quartet, agent/bearer vs target, condition vs exception.
- Established in schema but with little observed use, so the project would be an early adopter: Akoma Ntoso `quantity` in legislation, separate efficacy and application periods, LegalRuleML `Override` and `Bearer`.
- Not established anywhere I looked, so must be defined locally and labelled as such: rate, threshold, base, tax year, credit amount, phase-out.

### Gaps
- Production adoption of Akoma Ntoso (which parliaments and publishers use it, and which elements they populate) was not researched; the counts above come only from the specification's own examples.
- I did not count element usage in actual US Code USLM files (only the bill samples), so I cannot say how often `<chapeau>`, `<continuation>` or `<term>` occur in Title 26.
- No evidence was gathered on current LKIF Core use; I only confirmed the ontology files exist on GitHub.
